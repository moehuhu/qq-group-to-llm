# koishi-plugin-qq-group-to-llm

[![npm](https://img.shields.io/npm/v/koishi-plugin-qq-group-to-llm?style=flat-square)](https://www.npmjs.com/package/koishi-plugin-qq-group-to-llm)

记录 QQ 群消息，并接入 LLM 做群聊分析。

## 功能

- **消息记录**：监听群消息写入 `qq_group_messages` 表，消息元素序列化为纯文本（图片、引用是否展开可配置），同时留存发言者昵称与头像地址，不记录 bot 自身的消息
- **群聊分析**：`群分析` 命令调用 LLM 生成报告——热门话题、金句、活跃榜、24 小时活跃时段柱状图
- **高光对话**：`高光对话` 命令单独截取带学术要素的冷幽默对话片段，通栏聊天气泡排版
- **自由问答**：`群分析 <问题>` 就近期聊天记录提问，仅依据记录作答
- **用户画像**：`用户画像` 命令跨群汇总某人的发言生成画像，每次都基于最新发言重新生成，结论落库供缓存复用
- **图片输出**：`群分析` 报告与`用户画像`可渲染成排版好的图片发送（puppeteer），关掉或渲染失败自动回退为文字
- **用户屏蔽**：群分析 / 金句 / 高光对话 / 用户画像各有一份独立的屏蔽名单，按用户 ID 配置
- **时区可配**：`timezone` 统一决定分桶、展示与投喂给模型的时间戳
- **定期清理**：按 `retentionDays` 删除过期消息（0 表示永久保留）

## 命令

```
群分析                        # 分析最近 1 天，输出报告（别名 group-analysis）
群分析 -d 3                   # 分析最近 3 天
群分析 今天聊了什么部署的事    # 就记录自由提问
群分析 -f                     # 忽略缓存重新分析
群分析 -g <频道 ID>            # 私聊中指定目标频道
高光对话                      # 截取高光对话（别名 highlight）
高光对话 5                    # 本次最多截 5 段
高光对话 -d 3 -f              # 最近 3 天，忽略缓存
用户画像                      # 查看自己的画像（别名 user-persona）
用户画像 @某人                # 查看他人，需要 personaViewAuthority 权限
用户画像 -f                   # 忽略缓存重新生成
```

## LLM 接入

走 OpenAI 兼容的 `/chat/completions` 接口，任何兼容厂商都可以用，在插件配置的「LLM 接口」一节填写 `openaiEndpoint` / `openaiApiKey` / `openaiModel`。

结构化结果要求模型返回 markdown 代码块中的 YAML；五段提示词模板（话题 / 金句 / 高光对话 / 问答 / 用户画像）都可在配置的「提示词」一节改写，占位符见各项描述。

**默认走流式**（`llmStream`）。非流式时服务端要等整段生成完才发响应头，提示词一长就会撞上 undici 那 5 分钟的 `headersTimeout`，抛一个 `UND_ERR_HEADERS_TIMEOUT` 就没了——注意 Koishi 的 `timeout` 配置走的是 AbortController，管不到这个底层超时。流式下响应头秒回，只要分片不断就不会再触发超时。个别厂商不支持流式时可以关掉。

**失败会自动重试**（`llmRetries`，默认 2 次，退避 1s / 2s）。只对超时、连接中断、限流和 5xx 生效；鉴权失败、参数错误重试多少遍都一样，直接抛出去让你看到真正的原因。错误码可能被 cordis 和 undici 包好几层，判定时会沿 `cause` 链一路往下找。重试在并发名额内进行，短暂退避期间不放掉名额，免得被别的请求插队。

**并发受闸门控制**：`llmConcurrency`（默认 **2**）限定同时在飞的请求数，超出的排队等待。厂商对并发通常有限制，一次打太多会直接调用失败；设为 1 即完全串行。

闸门在 `LLMService` 内部，是全局唯一的一道——不管请求来自群分析、问答、用户画像，还是别的插件通过 `ctx.qqGroupLlm` 调过来，都算在同一个额度里，所以多人同时发命令也不会突破上限。请求失败会立刻归还名额，不会把后面排队的饿死。

一份 `群分析` 报告跑两次模型（话题 / 金句），两个一起发出，按默认上限 2 正好并行；`高光对话` 与`用户画像`各只跑一次。多条命令同时触发时由闸门统一限流。命令里那句「正在分析…请稍候」就是为此准备的。

`LLMService` 注册为 `ctx.qqGroupLlm` 服务，其他插件可直接复用。

## 时区

`timezone` 填 IANA 名称（如 `Asia/Shanghai`），留空则跟随运行 Koishi 的机器时区。它同时决定三处，三处必须一致，否则报告里的时间范围会和柱状图对不上：

- 活跃时段柱状图的分桶，以及深夜占比的判定
- 报告与画像里展示的时间范围
- 投喂给模型的逐条消息时间戳——模型回答「昨晚几点聊的」时依据的就是它

底层是 `Intl.DateTimeFormat`，不引第三方库，夏令时和 `Asia/Kolkata` 这种半小时偏移都由它处理。小时制固定 `h23`：默认的 `h24` 会把午夜写成 24，分桶时会多出一个不存在的下标。

时区名不认识时打一条 warn 后回落到系统时区，不会让命令失败。插件启动时会打一行当前生效时区与当下时间，对不上一眼就能看出来。

## 活跃时段

报告底部按**配置时区的整点**把发言量分成 24 格，画成柱状图。没人说话的整点保留空位，作息里的断档一眼能看见。

峰值那一柱用暖色挑出来并标出条数；深夜 00–06 点整体压暗，脚注给出这段时间的占比。这两处纯统计，不经过 LLM，也不消耗 token。

柱高按峰值归一，有发言的整点至少留 3px——不然「1 条」和「一条没有」看起来一模一样。窄画布（<820px）下 24 个小时标签仍不重叠，实测过。

走文字出口（未开图片渲染或渲染失败）时，这里退化成一行八级方块字符的迷你柱状图，例如 `▂▂       ▂  ▄▃    ▂   ▆█`，外加峰值说明——24 行逐时列表在聊天窗口里太占地方。

## 金句与高光对话

两者由两次独立的 LLM 抽取产生，判定标准互不干扰，**分属两条命令**：

- **✨ 金句**（随 `群分析` 报告产出）：单句就能成立的精彩发言——观点新颖、表达生动或有反差感，跳过热词堆砌和复读。`maxGoldenQuotes` 控制条数上限，设为 0 即不抽取。
- **🧊 高光对话**（`高光对话` 命令）：连续的多轮对话，须同时满足「有学术要素」（某学科的术语、定理、模型、论文或研究范式，不限理工科）和「是冷幽默」（笑点来自一本正经的推演与反差，而非感叹号、颜文字、网络热梗）。两条缺一不可。`maxHighlightDialogues` 控制段数上限，`maxHighlightLines` 控制单段最多几轮；命令带数字参数可临时改本次段数，不写回配置。

两类都是宁缺毋滥，找不到就返回空列表。报告里金句为空则整节不渲染；`高光对话` 一段都没找到时直接回一句话说明，不出图。

模型返回后还会再过一道规整：金句丢掉没有原文的；对话丢掉空轮次、按 `maxHighlightLines` 截断，并要求剩下的至少两轮、至少两人——一个人自问自答不算对话，会被整段丢弃。

## 用户屏蔽

配置里的「用户屏蔽」一节有四份**互相独立**的名单，填用户 ID：

| 配置项 | 作用 |
|---|---|
| `analysisUserFilter` | 「群分析」忽略这些人的发言——不进话题、不进活跃榜、不计入统计，自由问答也看不到 |
| `quoteUserFilter` | 「金句」不收录这些人 |
| `dialogueUserFilter` | 「高光对话」不收录这些人，含有他们的对话**整段**丢弃 |
| `personaUserFilter` | 不为这些人生成「用户画像」 |

分开而不是一份总名单，是因为诉求往往不一样：可以允许某人正常出现在话题和活跃榜里，只是不希望他的话被摘成金句。

屏蔽在**投喂之前**生效——被屏蔽者的发言根本不会进入提示词，模型看不到，也就编不出来。此外结果层还会按昵称再拦一道：屏蔽名单填的是用户 ID，而模型只认昵称，万一别人转述、或模型张冠李戴地把话安到被屏蔽者头上，光靠不投喂是拦不住的。高光对话在这一步整段丢弃——抽掉其中一轮，剩下的对话就接不上了。

被屏蔽者的消息**照常记录**，只是分析时不用。想恢复时把 ID 从名单里删掉即可，历史记录还在。

## 投喂给模型的对话文本

一条记录占一行，行首的 `[时间] 昵称:`（用户画像那边还多一个 `<msgid:…>` 锚点）把这一行的归属钉死。

麻烦在于正文未必只有一行。QQ 的「群聊的聊天记录」（合并转发）到了适配器手里是一整块多行文本，`[消息内容]` / `[发送者]` / `=== 消息 N ===` 这些排版行连同中间的空行全在里面。直接拼进去，第二行往后就成了没有行首标记的「无主发言」，正文里的空行还会被当成记录之间的分隔——模型于是把 `[发送者] 张三` 当成有人真说过的话，给后面几行张冠李戴地安发言人；画像那边的锚点也会错位到不属于它的行上，`evidence` 引用的原文就对不上了。转发的内容越长，错得越离谱。

所以正文的续行一律缩进四个空格：记录永远从行首开始，缩进的行只可能是上一条的延续。这一步只改排版，正文一个字都不增删（去掉续行缩进即可逐字还原），也不需要在提示词里额外交代——缩进本身就是续行的通用写法。单行消息（绝大多数情况）排出来的结果和以前完全一致。

## 图片输出

`renderImage` 打开时，`群分析` 报告和`用户画像`会先渲染成 HTML，再用 puppeteer 截成图发出；`imageWidth` 控制宽度（默认 1000 CSS 像素），`imageScale` 控制缩放倍率（默认 2，即二倍图，在 QQ 里缩放后文字不糊）。

**群分析**的分节一律通栏纵向堆叠，列数逐板块指定：

| 板块 | 列数 | 为什么 |
|---|---|---|
| 热门话题（群分析） | 2 | 话题卡不长，两列刚好 |
| 金句（群分析） | 3 | 金句短，一行一句太浪费横向空间 |
| 活跃榜（群分析） | 2 | 榜单行很扁，两列能省一半高度 |
| 高光对话（独立命令，整张图） | 1 | 聊天气泡要靠宽度才排得开，挤进窄列就没有对话的样子了 |

实际列数取「板块上限」与「条目数」的较小值——两条内容排三列会空出一列，一条内容排两列会空出一半。`imageWidth` 低于 820 时全部退回单列，每列不足 400px 时卡片里的文字会挤得没法读。

分栏用的是 grid 而非 `column-count`：多列流按列灌，4 张卡片分 3 列会被平衡成 2+2+0 白白空出一列；grid 按行铺，永远不会留空列。

**用户画像**仍是页面级两列（左结论、右原话），走的是另一条路径：分节整块地灌进两列，不拆。

puppeteer 是**可选**依赖。没装、没启用、或者渲染过程中出了任何错，都只会打一条 warn 然后回退到原来的 markdown 文本，命令本身不会失败。插件启动时会打一行日志说明当前走的是哪种出口。

头像来自消息记录：`qq_group_messages.avatar` 存的是**发言当时**的头像地址，渲染时按昵称回查。这样即使人已退群、或平台不支持事后查询，报告里也还有头像可用。高光对话的气泡和活跃榜都用它；用户画像优先用命令触发时抓到的头像，抓不到再依次回退到记录里的和库里的旧值。

平台塞在正文里、适配器没解析掉的内联标记会被清掉。QQ 的 `<faceType=6,faceId="…",ext="…">` 会被适配器换成图片元素，但缺 faceId/ext 的简写 `<faceType=6>` 匹配不上它的正则，于是原样留在文本里——表情本身已经是图片了，这个残标记纯属噪音，既显示在图里也跟着提示词喂给模型。清洗在**入库时**和**读取时**各做一次：前者让新记录干净，后者覆盖历史记录，两头都堵上后渲染和提示词都不用各清一遍；渲染层另有一道兜底，防模型把残标记原样抄回结果。

消息里的图片会还原成真正的图片。recorder 把图片元素序列化成 `[图片](地址)` 存进记录（`recordImages` 关闭时只留 `[图片]`），渲染时把这个占位符换成 `<img>`——不做这一步的话，群里发的图在报告里就是一行扎眼的 `[图片](https://...)` 原文。连续的图片并成一个块级容器自成一行：图片留在文字行里会把行高撑得老高，前后的文字被挤成上下两截。图链失效（QQ 的图片地址会过期）时自动退回一枚「🖼 图片」小标签，不会只剩一块空白。地址只放行 http(s)，其余协议按无地址处理。高光对话的气泡、报告里的金句、画像的代表发言都走这套。

版面是纯 CSS 手写的，不引任何外部资源——不依赖 CDN 字体，离线环境下渲染结果一致，截图前也不用等网络空闲。字体走系统栈（PingFang / 微软雅黑 / Noto Sans CJK 依次回退）。头像等远程图片会等加载完再截图，单张图最多等 3 秒，超时就按当前状态拍，不会把整次渲染拖死；头像加载失败时自动退回昵称首字的色块。

几处版面细节：高光对话按发言人还原成左右交替的聊天气泡，同一个人始终在同一侧；活跃榜的条形长度相对榜首按比例绘制，前三名有奖牌配色。头像统一是「首字色块打底、图片盖在上面」，没有地址或图挂了就露出底下的字，不会出现浏览器的破图图标；圆圈里的字对中文昵称取**末字**——群里「老王」「老李」这种前缀太常见，取首字几乎必然撞成同一个字。

## 用户画像

每次生成都只依据回溯窗口内的最新发言，不把已有结论回喂给模型，也不与旧画像做字段合并——结果完全由这批记录决定。画像以 YAML 存进 `qq_group_personas` 表，仅用于缓存复用；当发言条数不足或模型调用失败、本次无法产出时，会返回库里的旧画像并说明原因，而不是把它抹掉。

投喂给模型的每条消息都带 `<msgid:xxx>` 锚点，模型在 `evidence` 中引用这些 id，渲染前回查原文——查不到的 id 直接丢弃，模型编不出不存在的「代表发言」。

默认汇总该用户在所有已记录频道的发言，`personaOnlyCurrentGroup` 可限制为当前频道；`personaCacheDays` 天内复用已有结果，`-f` 跳过。

命令触发时会抓取画像主人的头像并存进 `qq_group_personas.avatar`，结果消息里作为图片附在文字前面。看自己的画像时头像直接来自会话；看他人时走 `bot.getUser()`，平台不支持就省略头像，不影响画像本身。本次没抓到时沿用库里已存的旧值。

## 调试

日志统一挂在 `qq-group-to-llm` 名下，在控制台的日志页按这个名字过滤即可。

`info` 级别覆盖关键路径：插件启动的生效配置、监听范围、每次 LLM 请求的模型/提示词长度/耗时/**token 用量**、**LLM 的完整返回原文与解析后的结构**、取数条数与是否触顶截断、缓存命中、命令由谁在哪里发起、画像更新与合并方式。

请求因名额已满而排队时会打一条 info，写明当前在飞数与上限；卡住时看这条日志就知道是在排队还是在等模型。

`warn` 覆盖可疑但不致命的情况：提示词有未替换的占位符、模型没按 YAML 格式返回、画像引用了不存在的 msgid（会列出被丢弃的 id）、子任务失败导致报告某段留空。

出错时一律打全文不截断：没按格式返回时打完整响应，YAML 语法错时打完整 YAML，接口返回空时打完整响应体（含厂商的 error 字段，比如 `insufficient_quota`）。

把日志级别调到 `debug` 会额外打印**完整提示词**——里面含几百条群消息，很吵，按需开启。API Key 在任何级别都不会进日志。

请求超时或中断时，日志里会先打一行归纳好的原因（`HTTP 429 | UND_ERR_HEADERS_TIMEOUT | ...`）再打原始错误对象，不用自己在层层嵌套的 `cause` 里翻。

嫌 `info` 里的完整响应太吵，把 `llm/index.ts` 里那两行 `完整响应` / `解析出` 的 `log.info` 改回 `log.debug` 即可。注意 reggol 对**单行**超过 10240 字会截断，YAML 是多行的所以不受影响。

```
    ├── analysis.ts     群分析 / 自由问答
    ├── highlights.ts   高光对话
    └── persona.ts      用户画像
```

依赖是单向的：`logger` 和 `types` 是叶子，`config`、`database` 只依赖它们，`llm` 与 `message` 建立在这之上，`analysis` 与 `render` 再往上，`commands` 位于最外层。统计与两种渲染（markdown / HTML）都被拆成不依赖 `Context` 的纯函数，可以脱离 Koishi 单独测试。
