# koishi-plugin-qq-group-to-llm

[![npm](https://img.shields.io/npm/v/koishi-plugin-qq-group-to-llm?style=flat-square)](https://www.npmjs.com/package/koishi-plugin-qq-group-to-llm)

记录群消息，并接入 LLM 做群聊分析：话题总结、金句、高光对话、自由问答、用户画像，结果可以直接出图。

## 功能

- **消息记录**：监听群消息写入 `qq_group_messages` 表，元素序列化为纯文本（图片/视频地址是否留存可配置，引用会带上被回复者的昵称与原话，合并转发压成一行一句），同时留存发言者昵称与头像地址
- **群聊分析**：`群分析` 出一份报告——热门话题、金句、活跃榜、24 小时活跃时段柱状图
- **高光对话**：`高光对话` 单独截取带学术要素的冷幽默对话片段，通栏聊天气泡排版
- **自由问答**：`群分析 <问题>` 就近期记录提问，只依据记录作答
- **用户画像**：`用户画像` 跨群汇总某人的发言生成画像，每次都基于最新发言重新生成
- **图片输出**：三条命令都能渲染成排版好的图片发送（puppeteer），关掉或渲染失败自动回退为文字
- **用户屏蔽**：群分析 / 金句 / 高光对话 / 用户画像各有一份独立的屏蔽名单
- **时区可配**：`timezone` 统一决定分桶、展示与投喂给模型的时间戳
- **定期清理**：按 `retentionDays` 删除过期消息，0 为永久保留

## 快速开始

1. 装好数据库插件（任意 Koishi 支持的驱动）；`database` 与 `http` 是必需服务，`puppeteer` 可选，用于出图。
2. 在「LLM 接口」一节的 `llmModels` 命名模型列表里至少填一个模型（端点、API Key、模型名），任何兼容 OpenAI `/chat/completions` 的厂商都行。想让不同任务用不同模型，再多加几个模型并在各任务里指定，见「LLM 接入」。
3. 默认 `listenAll` 开着，插件会记录所有群的消息。攒够 `minMessages`（默认 20）条之后，在群里发 `群分析`。

没配 API Key 时插件照常记录消息，只是分析类命令用不了，启动日志里会点出来。

## 命令

```
群分析                        # 分析最近 1 天，出一份报告（别名 group-analysis）
群分析 -d 3                   # 改成最近 3 天（1–7）
群分析 今天聊了什么部署的事    # 带参数即转为自由问答，只依据记录作答
群分析 -f                     # 忽略缓存重新分析
群分析 -g <频道 ID>            # 私聊里指定目标频道

高光对话                      # 截取高光对话（别名 highlight）
高光对话 5                    # 本次最多截 5 段，不写回配置
高光对话 -d 3 -f              # 最近 3 天，忽略缓存

用户画像                      # 看自己的画像（别名 user-persona）
用户画像 @某人                # 看他人，需要 personaViewAuthority 权限
用户画像 -f                   # 忽略缓存重新生成
```

## 消息记录

监听 `message` 事件，把符合条件的消息写进 `qq_group_messages` 表。

- **范围**：`listenAll` 开着就记录所有群；关掉则只记 `groups` 列表里的，格式 `平台:频道 ID`，两段都可以留空当通配。私聊不记，bot 自己发的不记。
- **序列化**：消息元素拍平成纯文本。媒体统一是 `[图片]` / `[视频]` / `[语音]` / `[文件]` 这一套占位符，图片与视频按 `recordImages` 带上地址（`[图片](地址)`），语音、文件只留类型；提及与引用见下面两条；表情见下一节；其余元素退化成 `[类型]`。
- **适配器漏掉的附件会补回来**：adapter-qq-crack 转图片时按 `content_type.startsWith('image')` 认，转视频和语音却要求 content_type **精确等于** `'video'` / `'voice'`——而 QQ 下发的是 MIME（`video/mp4`、`audio/amr`），那两个分支等于死代码。于是一条纯视频消息在 `session.elements` 里一个元素都不剩，正文也是空的，落库就是一条什么都没有的空记录。
  所以从平台原始载荷（`session.event._data`，适配器 `setInternal` 挂上去的）里按地址比对补一遍：已经转成元素的不补第二遍，哪天适配器修好了这里自然不再出手。别的平台形状对不上就是空数组，什么都不补。
- **解析不出内容的消息不入库**：空记录白占一条条数、把人均字数往下拉，投喂给模型的文本里还留一行没有内容的发言。跳过时打一条 `warn`（带元素类型与原始附件数），好让下一种没人认得的消息类型露出来。
- **提及**：@ 别人存成 `[@张三]`，@全体成员存成 `[@全体成员]`，@ 到 bot 自己的存成 bot 的昵称。

  名字**连着 @ 一起包在方括号里**，跟 `[引用 昵称]` 是同一个道理——渲染那边要断得出边界。只写 `@张三` 的话，遇上「@张三你看看」这种紧接着说下去的（群里最常见的写法）就分不清哪一截是名字：@ 后面没有收尾符号，名字有多长全靠猜。

  麻烦在于 QQ 的 at 元素上**只有一个 openid，没有名字**。名字按四条来路依次找：元素自带的 `name`（别的平台的适配器会一并给上）→ 平台原始载荷的 `mentions` 列表按 id 对上 → @ 的是 bot 自己（adapter-qq-crack 会把 bot 的 at 改写成 `selfId`，而 `mentions` 里记的是 bot 的 openid，两边对不上，得单拎出来认）→ 先前记下的名字。

  最后那条来路是一本跟着插件走的名册（`平台:用户 ID` → 昵称，上限 2000 人，满了先扔最久没露面的，卸载即丢）：每见到一个名字就记下来。被引用的那条、转发卡片里的那几条，它们的 at 不在当前这份 `mentions` 里，只有靠名册才认得出是谁。

  四条都落空才退成 `[@某人]`——**不把 ID 填进去**：QQ 给的是三十多位的 openid，摆在正文里既不是人话，出图时还能撑破一行；它和记录里的昵称也对不上，模型拿它接不到任何一个人身上，纯是白烧 token。

  早先 at 元素没人认，落到序列化的兜底分支存成一个光秃秃的 `[at]`——@ 的是谁没了不说，这三个字母混在中文正文里，模型也读不出它是一次提及。历史记录在读取时就地换成 `[@某人]`；两侧贴着字母、数字、点号的不认（`zhang[at]qq.com` 是群里躲爬虫的邮箱写法，不是提及）。

  出图时提及排成一枚淡靛标签，字号跟着它落在的那一处走（气泡、引用条、转发卡片三处正文的字号各不相同）。
- **引用**：回复别人的消息，被引用的那条会压成正文首行 `[引用 昵称] 原话`，正文接在第二行起。
  引用元素到了 QQ 适配器手里往往只是个带 messageId 的空壳，所以原话取自 `session.quote`——只看元素的话，回的是谁、回的是哪句就全丢了，模型读到的一来一回也接不上。
  原话压成一行并截到 60 字（被引用的那条自己也在库里，不必抄第二份），昵称截到 24 字并剔掉方括号与换行，免得破掉 `[引用 昵称]` 这对边界。关掉 `recordQuotes` 就只留一个 `[引用]`。出图时这一行渲染成正文上方的引用条。
- **合并转发**：QQ 的「群聊的聊天记录」不是结构化数据，而是平台自己排好版的一整块文本。纯文字的那条是 `[消息内容]` + `[发送者]`；带图的那条**没有 `[消息内容]`**，图挂在 `[附件N]` 上，字段顺序还反过来：

  ```
  === 消息 2 ===
  [发送者] 李四
  [附件1] 类型:图片 文件名:x.jpg 尺寸:1920x864 大小:72.2KB URL:https://…
  ```

  一条转发四五行里只有一两行是人说的话：喂给模型是白烧 token，出图是一堆 `=== 消息 N ===` 和文件名尺寸糊在气泡里，发文字更惨——markdown 出口会把换行压成空格，整块挤成一长条。
  所以入库前就压成一行一句、谁说的写在前面，附件换成正文里通用的占位符（原话一个字不动，只是去掉排版行、把发送者提到前面）：

  ```
  [群聊的聊天记录]
  张三: 你好
  李四: [图片](https://…)
  ```

  只有图片带地址——出图时它能换成真正的图片，别的类型（`[视频]` / `[语音]` / `[文件]` / `[附件]`）给了地址也渲染不出来，白白在正文里留一串两百多字符的 URL；文件名、尺寸、大小一律丢掉。图片地址是否留存跟 `recordImages` 走。
  出图时这块渲染成一张两列的记录卡片，名字与正文各占一列对齐，图片按缩略图排（一条转发裹着七八张图，按气泡里的尺寸排下来能顶半页），超过 8 条折成「还有 N 条」。
- **多层转发**：转发是能套娃的——里头的某一条本身又是一整份聊天记录。两种分隔行各管一层：`=== 消息 N ===` 和 `--- 第N条 ---`，谁先出现谁是外层，另一种就是里层（不写死谁是外层：引用回来的转发用的就是 `--- 第N条 ---` 打头）。里层的内容整段不收，只留一个缩略标题，条数取里层分隔行上的最大序号：

  ```
  [群聊的聊天记录]
  张三: [群聊的聊天记录 4 条]
  张三: [群聊的聊天记录 4 条]
  ```

  不折叠的话，一份四层套娃展开就是几十行图片平铺在外层列表里，既看不出层次，也把报告和提示词撑爆。出图时这个标题排成一枚标签，跟正文区分开。
- **单条形态**：没有标题也没有分隔行、整段只是一条消息的排版树时，只留正文与附件。引用回来的那条就长这样——适配器会把 `[发送者] 某某` 一起漏进引用内容里，图片消息则只剩一行 `[附件1]`；是谁说的，引用预览已经从 `session.quote` 拿到了，不必再抄一遍。
- **一起留存的还有发言者昵称和头像地址**——事后渲染时人可能已经退群，平台接口未必还查得到。
- **保留期**：`retentionDays` 天，`0`（默认）为永久保留。启用后每 6 小时清一次过期记录。

画像结果另存在 `qq_group_personas` 表，见「用户画像」。

## 表情与图片的还原

平台塞在正文里、适配器没解析掉的内联表情标记会被**还原成它显示的名字**。QQ 的表情在正文里长这样：

```
<faceType=4,faceId="",ext="eyJ0ZXh0IjoiW+Wuieivpl0ifQ==">
```

`ext` 是一段 base64，解出来是 `{"text":"[安详]"}`——正是这个表情在 QQ 里显示的名字，于是它被还原成 `[安详]`。官方适配器会把这段拆成 emoji 元素，有的第三方适配器则直接把整段 content 塞进一个文本元素，标记就原样留在正文里了；两种形式都认。

`faceType=6`（动画表情 / 超级 QQ 秀 / GIF）是例外：图本身在 attachments 里，适配器已经单独给过一个图片元素，再还原一次就是重复的两份，所以只把标记删掉。缺 `ext` 的简写 `<faceType=6>`、`ext` 解不出名字的，同样直接删掉。

还原在**入库时**和**读取时**各做一次：前者让新记录干净，后者顺带覆盖历史记录，两头都堵上后渲染和提示词都不用各处理一遍；渲染层另有一道兜底，防模型把残标记原样抄回结果。合并转发的压平挂在同一条路上（`cleanContent` = 还原残标记 + 压平转发），所以历史记录读出来也就地跟上，重复跑是空转。

图片则在出图时还原成真正的图片：`[图片](地址)` 占位符换成 `<img>`，不做这一步的话群里发的图在报告里就是一行扎眼的 `[图片](https://...)` 原文。连续的图片并成一个块级容器自成一行——图片留在文字行里会把行高撑得老高，前后的文字被挤成上下两截。图链失效（QQ 的图片地址会过期）时退回一枚「图片」小标签，不会只剩一块空白；地址只放行 http(s)。

视频画成一块带播放标记的占位块，**不放 `<video>`**：截图跑在 puppeteer 里，视频既不解码也不会停在第一帧，拿到的就是一块黑；QQ 的地址还几分钟就过期，等于给报告留一块必然失效的空白。播放三角用 CSS 边框画，不写 `▶` 字符——没装 emoji 字体的机器上那会变成方框。地址照旧留在记录里，只是不参与渲染。语音、文件没什么可展示的，当普通文字排。
合并转发另起一张两列卡片（标题 + `名字 | 正文`），超过 8 条折成「还有 N 条」——转发几十条的截图会长得没法看。高光对话的气泡、报告里的金句、画像的代表发言都走这套。

## 投喂给模型的对话文本

一条记录占一行，行首的 `[时间] 昵称:`（用户画像那边还多一个 `<msgid:…>` 锚点）把这一行的归属钉死。

麻烦在于正文未必只有一行。最常见的是合并转发：一条消息里裹着好几个人的发言（排版块在入库时已经压成一行一句，见上文）。直接拼进去，第二行往后就成了没有行首标记的「无主发言」，正文里的空行还会被当成记录之间的分隔——模型于是把转发里的话算到别人头上，给后面几行张冠李戴地安发言人；画像那边的锚点也会错位到不属于它的行上，`evidence` 引用的原文就对不上了。转发的内容越长，错得越离谱。

所以正文的续行一律缩进四个空格：

```
[10:22:28] 张三: [群聊的聊天记录]
    李四: 你好
    王五: 我这有个多行的
        第二行
[10:22:39] 张三: 下一条
```

记录永远从行首开始，缩进的行只可能是上一条的延续。这一步只改排版，正文一个字都不增删（去掉续行缩进即可逐字还原），也不需要在提示词里额外交代——缩进本身就是续行的通用写法。单行消息（绝大多数情况）排出来的结果和不做这件事时完全一致。

## LLM 接入

走 OpenAI 兼容的 `/chat/completions` 接口。结构化结果要求模型返回 markdown 代码块里的 YAML；五段提示词模板（话题 / 金句 / 高光对话 / 问答 / 用户画像）都能在配置的「提示词」一节改写，占位符见各项描述。

**模型只能通过命名模型列表配置**：在「LLM 接口」一节的 `llmModels` 里定义若干模型，每个都填自己的端点、key、模型名与温度（支持任意兼容 OpenAI 接口的厂商），再把「话题总结 / 金句提取 / 高光对话 / 群聊问答 / 用户画像」各自的「模型」填成对应的模型 id 即可。比如让金句和画像用贵一点的大模型、话题与问答用便宜快的小模型：

```yaml
llmModels:
  - id: cheap
    endpoint: https://api.openai.com/v1
    apiKey: sk-xxxx
    model: gpt-4o-mini
    temperature: 1
  - id: fancy
    endpoint: https://other-vendor.example/v1
    apiKey: sk-yyyy
    model: some-big-model
    temperature: 0.7
llmModelTopic: cheap
llmModelQuery: cheap
llmModelGoldenQuotes: fancy
llmModelUserPersona: fancy
llmModelHighlightDialogues: cheap
```

任务的「模型」留空或填了不存在的 id 时，回落到 `llmModels` 里的第一个，并打一条警告。只填一个模型就能让所有任务共用它，不必多配。

多个命名模型共用同一道并发闸门，配额按请求数算，不看模型或厂商。

**默认走流式**（`llmStream`）。非流式时服务端要等整段生成完才发响应头，提示词一长就会撞上 undici 那 5 分钟的 `headersTimeout`，抛一个 `UND_ERR_HEADERS_TIMEOUT` 就没了——注意 Koishi 的 `timeout` 配置走的是 AbortController，管不到这个底层超时。流式下响应头秒回，只要分片不断就不会再触发超时。个别厂商不支持流式时可以关掉。

**失败会自动重试**（`llmRetries`，默认 2 次，退避 1s / 2s）。只对超时、连接中断、限流和 5xx 生效；鉴权失败、参数错误重试多少遍都一样，直接抛出去让你看到真正的原因。错误码可能被 cordis 和 undici 包好几层，判定时会沿 `cause` 链一路往下找。重试在并发名额内进行，短暂退避期间不放掉名额，免得被别的请求插队。

**并发受闸门控制**：`llmConcurrency`（默认 2）限定同时在飞的请求数，超出的排队等待。厂商对并发通常有限制，一次打太多会直接调用失败；设为 1 即完全串行。闸门在 `LLMService` 内部，是全局唯一的一道——不管请求来自群分析、问答、用户画像，还是别的插件通过 `ctx.qqGroupLlm` 调过来，都算在同一个额度里，所以多人同时发命令也不会突破上限。请求失败会立刻归还名额，不会把后面排队的饿死。

一份 `群分析` 报告跑两次模型（话题 / 金句），两个一起发出，按默认上限 2 正好并行；`高光对话` 与 `用户画像` 各只跑一次。命令里那句「正在分析…请稍候」就是为此准备的。

`LLMService` 注册为 `ctx.qqGroupLlm` 服务，其他插件可直接复用。

## 群分析报告

`群分析` 不带参数时出一份报告，含四块内容：

- **概览**：消息数、参与者数、总字数、最活跃时段
- **热门话题**：模型提取，最多 `maxTopics` 个，每个带参与者与来龙去脉。模型还需为每个话题附上支撑它的原话记录作内部核对依据——防止张冠李戴，这些原话不会展示在结果里
- **金句**：见下一节，`maxGoldenQuotes` 为 0 时整节不出现
- **活跃榜**：发言数排行，取前 `maxUsersInReport` 名，带条形图与均字数
- **活跃时段**：24 小时柱状图，见下文

取数是「最近 `days` 天的最后 `maxMessages` 条」，不足 `minMessages` 条直接回一句话说明，不调模型。结果按 `频道:天数` 缓存 `cacheMinutes` 分钟，`-f` 跳过；自由问答不走缓存。

任一子任务（话题 / 金句）失败只让那一块留空，不会拖垮整份报告。

### 活跃时段

按**配置时区的整点**把发言量分成 24 格。没人说话的整点保留空位，作息里的断档一眼能看见；峰值那一柱用暖色挑出来并标出条数，深夜 00–06 点整体压暗，脚注给出这段时间的占比。这一块纯统计，不经过 LLM，也不消耗 token。

柱高按峰值归一，有发言的整点至少留 3px——不然「1 条」和「一条没有」看起来一模一样。

走文字出口时退化成一行八级方块字符的迷你柱状图，例如 `▂▂       ▂  ▄▃    ▂   ▆█`，外加峰值说明——24 行逐时列表在聊天窗口里太占地方。

## 金句与高光对话

两者由两次独立的抽取产生，判定标准互不干扰，**分属两条命令**：

- **金句**（随 `群分析` 报告产出）：单句就能成立的精彩发言——观点新颖、表达生动或有反差感，跳过热词堆砌和复读。`maxGoldenQuotes` 控制条数上限，设为 0 即不抽取。
- **高光对话**（`高光对话` 命令）：连续的多轮对话，须同时满足「有学术要素」（某学科的术语、定理、模型、论文或研究范式，不限理工科）和「是冷幽默」（笑点来自一本正经的推演与反差，而非感叹号、颜文字、网络热梗）。两条缺一不可。`maxHighlightDialogues` 控制段数上限，`maxHighlightLines` 控制单段最多几轮；命令带数字参数可临时改本次段数，不写回配置。

分成两条命令是因为篇幅差得远：高光对话保留多轮上下文，混进报告会把报告撑得很长。

两类都是宁缺毋滥，找不到就返回空列表。报告里金句为空则整节不渲染；`高光对话` 一段都没找到时直接回一句话说明，不出图。

模型返回后还会再过一道规整：金句丢掉没有原文的；对话丢掉空轮次、按 `maxHighlightLines` 截断，并要求**截断之后**剩下的至少两轮、至少两人——一个人自问自答不算对话，会被整段丢弃。

## 用户画像

每次生成都只依据 `personaLookbackDays` 天内的最新发言，不把已有结论回喂给模型，也不与旧画像做字段合并——结果完全由这批记录决定。画像以 YAML 存进 `qq_group_personas` 表，仅用于缓存复用；当发言条数不足或模型调用失败、本次无法产出时，会返回库里的旧画像并说明原因，而不是把它抹掉。

投喂给模型的每条消息都带 `<msgid:xxx>` 锚点，模型在 `evidence` 里引用这些 id，渲染前回查原文——查不到的 id 直接丢弃，模型编不出不存在的「代表发言」。

默认汇总该用户在所有已记录频道的发言，`personaOnlyCurrentGroup` 可限制为当前频道；`personaCacheDays` 天内复用已有结果，`-f` 跳过。看他人的画像需要 `personaViewAuthority` 级权限（默认 3）。

头像优先用命令触发时抓到的：看自己时直接来自会话，看他人时走 `bot.getUser()`，平台不支持就依次回退到消息记录里的和库里的旧值，都没有也只是不展示头像，不影响画像本身。

## 用户屏蔽

配置里的「用户屏蔽」一节有四份**互相独立**的名单，填用户 ID：

| 配置项 | 作用 |
|---|---|
| `analysisUserFilter` | 「群分析」忽略这些人的发言——不进话题、不进活跃榜、不计入统计，自由问答也看不到 |
| `quoteUserFilter` | 「金句」不收录这些人 |
| `dialogueUserFilter` | 「高光对话」不收录这些人，含有他们的对话**整段**丢弃 |
| `personaUserFilter` | 不为这些人生成「用户画像」 |

分开而不是一份总名单，是因为诉求往往不一样：可以允许某人正常出现在话题和活跃榜里，只是不希望他的话被摘成金句。

屏蔽在**投喂之前**生效——被屏蔽者的发言根本不会进入提示词，模型看不到，也就编不出来。此外结果层还会按昵称再拦一道：屏蔽名单填的是用户 ID，而模型只认昵称，万一别人转述、或模型张冠李戴地把话安到被屏蔽者头上，光靠不投喂是拦不住的。高光对话在这一步整段丢弃——抽掉其中一轮，剩下的对话就接不上了。

被屏蔽者的消息**照常记录**，只是分析时不用。想恢复时把 ID 从名单里删掉即可，历史记录还在。

## 图片输出

`renderImage` 打开时，`群分析`、`高光对话` 和 `用户画像` 会先渲染成 HTML，再用 puppeteer 截成图发出；`imageWidth` 控制宽度（默认 1000 CSS 像素），`imageScale` 控制缩放倍率（默认 2，即二倍图，在 QQ 里缩放后文字不糊）。

puppeteer 是**可选**依赖。没装、没启用、或者渲染过程中出了任何错，都只会打一条 warn 然后回退到 markdown 文本，命令本身不会失败。启动日志里会写明当前走的是哪种出口。

### 分栏

群分析的分节一律通栏纵向堆叠，列数逐板块指定：

| 板块 | 列数 | 为什么 |
|---|---|---|
| 热门话题 | 2 | 话题卡不长，两列刚好 |
| 金句 | 3 | 金句短，一行一句太浪费横向空间 |
| 活跃榜 | 2 | 榜单行很扁，两列能省一半高度 |
| 高光对话（独立命令，整张图） | 1 | 聊天气泡要靠宽度才排得开，挤进窄列就没有对话的样子了 |

实际列数取「板块上限」与「条目数」的较小值——两条内容排三列会空出一列，一条内容排两列会空出一半。`imageWidth` 低于 820 时全部退回单列，每列不足 400px 时卡片里的文字会挤得没法读。

分栏用的是 grid 而非 `column-count`：多列流按列灌，4 张卡片分 3 列会被平衡成 2+2+0 白白空出一列；grid 按行铺，永远不会留空列。

用户画像仍是页面级两列（左结论、右原话），走的是另一条路径：分节整块地灌进两列，不拆。

### 字体与 emoji

版面文案里**不写 emoji**。截图跑在 puppeteer 里，字体栈全是系统字体，标题上的图标一旦缺字就是方框；分节标题靠字重和那条渐变分隔线区分，不靠图标。走 markdown 那条出口不受这条约束——emoji 由聊天客户端自己渲染，那边照旧用。

**但群消息里的 emoji 是数据，得照常渲染出来**，所以字体栈里点名了 `Apple Color Emoji` / `Segoe UI Emoji` / `Noto Color Emoji` 等几个彩色 emoji 族。位置有讲究：排在正文字体**之后**，中英文先由正文字体挑走，`©` `®` `▶` 这类符号不会被顺手换成彩图；排在 `sans-serif` **之前**，泛型族一定匹配得上，放在它前面结果更确定。

光在 CSS 里点名不够，机器上得真装着字体。Debian/Ubuntu 装 `fonts-noto-color-emoji`，Alpine 装 `font-noto-emoji`——Koishi 官方 Docker 镜像基于 Alpine，只带了 `font-noto-cjk`，需要在镜像里补上。没装也只是 emoji 显示成方框，其余版面照常，不会让渲染失败。

正文字体走系统栈（PingFang / 微软雅黑 / Noto Sans CJK 依次回退）。版面是纯 CSS 手写的，不引任何外部资源——不依赖 CDN 字体，离线环境下渲染结果一致，截图前也不用等网络空闲。

### 头像与版面细节

头像来自消息记录：`qq_group_messages.avatar` 存的是**发言当时**的地址，渲染时按昵称回查。这样即使人已退群、或平台不支持事后查询，报告里也还有头像可用。

头像统一是「首字色块打底、图片盖在上面」，没有地址或图挂了就露出底下的字，不会出现浏览器的破图图标；圆圈里的字对中文昵称取**末字**——群里「老王」「老李」这种前缀太常见，取首字几乎必然撞成同一个字。底色由昵称派生，同一个人每次渲染颜色一致。

高光对话的气泡逐轮自上而下、一律靠左，发言人靠头像和名字区分。正文按 15.5px 排（比报告里其他文字大一档）——聊天记录是这张图的主角，1000px 宽的画布上按 14px 排在手机上看太吃力。**头像顶对齐**：底对齐时，一条带图或带转发卡片的发言能有两三百像素高，头像被推到最底下，和顶上的名字隔了大半个气泡，谁说的就对不上号了；气泡的缺口也跟着开在左上角，对着头像。活跃榜的条形长度相对榜首按比例绘制，前三名有奖牌配色。远程图片会等加载完再截图，单张最多等 10 秒，超时就按当前状态拍，不会把整次渲染拖死。

### 自定义版面

版面开放在配置里，改完不用动代码。页面模板与样式表都按三个出口各一份，分别维护——给群分析换个配色，不会顺手把画像那张图也改了：

| 配置项 | 作用 |
| --- | --- |
| `extraCss` | 追加样式，**三张图共用**，接在各自的样式表之后，同名规则覆盖前面的 |
| `reportHtmlTemplate` / `reportCssTemplate` | 「群分析」的页面模板与样式表 |
| `dialoguesHtmlTemplate` / `dialoguesCssTemplate` | 「高光对话」的页面模板与样式表 |
| `personaHtmlTemplate` / `personaCssTemplate` | 「用户画像」的页面模板与样式表 |

除 `extraCss` 外，各项预填的就是内置默认值，照着改即可；**清空则回到内置那份**（插件更新时也会跟着更新）。

三份样式表是各自完整的 CSS，共用的段落（重置、配色变量、分节、消息正文、页脚）在每份里都有一套，独有的只出现在对应那份里：数字条、话题、金句、活跃榜、柱状图只在群分析，气泡与对话脚注只在高光对话，头部资料、要点、代表发言与页面级分栏只在用户画像。

**只想换配色就用 `extraCss`。** 版面的颜色全走 `#card` 上的 CSS 变量，重写几个变量即可，一次对三张图都生效，也不必把哪份样式表整个复制一遍——这样插件后续更新版面时，改动不会被盖掉：

```css
#card {
  --accent: #ff6b6b;
  --accent-2: #ff9f43;
  --accent-soft: #fff1f1;
  --surface-2: #fff8f5;
}
```

#### 独立窗口里的实时预览

控制台装了 `console` 插件时，本插件的设置页会多出一行「版面预览」，点「在新窗口打开」会**弹出一扇独立窗口**：三个出口各一个标签页，用一份写死的示例数据渲染。

预览**不放在设置页里**——模板和样式表都是大段文本，跟表单挤在同一页时，改一行 CSS 得来回滚动才能看到效果。两扇窗口并排摆着，左边改右边看，才谈得上边改边看。

窗口里的内容**跟着编辑实时刷新**：模板、样式表、图片宽度任意一项改动，不用点保存就立刻重画。渲染走的是出图时同一套函数（`src/render/html.ts`），不是另写一套近似的界面，所以看到什么样，截出来就是什么样。示例数据刻意把引用、提及、图片、合并转发、多人排行榜、有峰值也有深夜的柱状图都塞了进去——这些边角情况最容易被自定义样式改坏。

几个细节：

- 报告塞在 iframe 里。样式表里全是 `body`、`*`、`.section` 这类通用选择器，漏出去会把预览窗口自己的工具条改花。
- 画面按窗口宽度等比缩放并居中，窗口拉宽就看得更清楚；图片的实际宽度由 `imageWidth` 决定，预览不改它。
- 模板或样式表写出异常时，预览位置显示一行报错，不会把设置页或预览窗口带崩。
- 关掉预览窗口，按钮自己复位；离开设置页时窗口一并关掉——留一扇不再更新的窗口在那儿只会让人误会。
- 弹窗被浏览器拦截时按钮旁边会提示，允许一次即可。

界面用 React 19 写（`client/Preview.tsx`、`client/Launcher.tsx`），外面套一层 Vue 壳挂进控制台（`client/mount.ts`）——控制台本身是 Vue 3 的，插槽只收 Vue 组件。预览窗口里是一个独立的 React 根：把父窗口的根 portal 过去也能渲染，但事件监听挂在父文档上，弹窗里的按钮就点不动了。代价是 react + react-dom 会打进控制台扩展包，产物约 230KB。

没装 `console` 时这段整个跳过，插件照常工作。

#### 页面模板的占位符

三份模板都是一整篇 HTML 文档，`{...}` 由插件填入渲染好的板块。公共的三个：`{title}` 标题（已转义）、`{width}` 图片宽度、`{style}` 该出口的样式表。各自独有的：

| 模板 | 独有占位符 |
| --- | --- |
| `reportHtmlTemplate` | `{groupName}` `{timeRange}`；`{stats}` 数字条；四个分节 `{topics}` `{quotes}` `{ranks}` `{hourly}`；四个原始数值 `{totalMessages}` `{totalParticipants}` `{totalChars}` `{mostActivePeriod}` |
| `dialoguesHtmlTemplate` | `{groupName}` `{timeRange}`；`{dialogues}` 全部对话段；`{count}` 段数；`{totalMessages}` 取样条数 |
| `personaHtmlTemplate` | `{name}` `{userId}`；`{avatar}` 头像元素；三个分节 `{summary}` `{points}` `{evidence}`；`{columns}` 分栏开关 |

分节占位符可以随意调换先后来改版面，删掉哪个那一节就不出现。群分析默认排 `{topics}{quotes}{ranks}{hourly}`，想把活跃榜提到最前面，把它挪到最左边即可。画像的 `{columns}` 拼在 `.body` 的 class 上，画布够宽且分节多于一个时才是 `columns`，删掉它就是恒定单列——页面级分栏只有画像用得上，另外两张图的多列发生在板块内部，走的是 `.group` 那张网格。

有几条约束：

- **`#card` 必须保留**：截图按这个元素的实际高度裁切，找不到它就退化成整页视口截图，底下会拖一大块空白。
- 板块内部那些 class（`.banner` `.section` `.rank` `.bubble` 等）由 `render/html.ts` 写死，换样式表时对着这些名字写；一条都不认得的样式表只会得到一张裸 HTML 的截图，不会让渲染失败。
- 名字对不上的占位符**原样留在页面上**，写错时看得见，不会悄悄渲染成一块空白让人以为是数据缺了。
- 占位符只填一遍，填进去的内容不再参与匹配——群消息里出现一句 `{ranks}` 不会把活跃榜复制到那个位置上去。

## 时区

`timezone` 填 IANA 名称（如 `Asia/Shanghai`），留空则跟随运行 Koishi 的机器时区。它同时决定三处，三处必须一致，否则报告里的时间范围会和柱状图对不上：

- 活跃时段柱状图的分桶，以及深夜占比的判定
- 报告与画像里展示的时间范围
- 投喂给模型的逐条消息时间戳——模型回答「昨晚几点聊的」时依据的就是它

底层是 `Intl.DateTimeFormat`，不引第三方库，夏令时和 `Asia/Kolkata` 这种半小时偏移都由它处理。小时制固定 `h23`：默认的 `h24` 会把午夜写成 24，分桶时会多出一个不存在的下标。

时区名不认识时打一条 warn 后回落到系统时区，不会让命令失败。插件启动时会打一行当前生效时区与当下时间，对不上一眼就能看出来。

四份屏蔽名单见「用户屏蔽」；`renderImage`（`true`）、`imageWidth`（`1000`，480–1600）、`imageScale`（`2`，1–3）见「图片输出」；`extraCss`（空）与三个出口各自的页面模板、样式表（`report*` / `dialogues*` / `persona*`，共六项）见「自定义版面」；五段提示词模板见「LLM 接入」。

## 调试

日志统一挂在 `qq-group-to-llm` 名下，在控制台的日志页按这个名字过滤即可。

`info` 覆盖关键路径：启动时的模型 / 并发 / 时区 / 出口方式与监听范围，每次 LLM 请求的模型、提示词长度、耗时和 **token 用量**，**模型的完整返回原文与解析后的结构**，取数条数与是否触顶截断，缓存命中，命令由谁在哪里发起，画像更新。请求因名额已满而排队时也会打一条，写明当前在飞数与上限——卡住时看这条就知道是在排队还是在等模型。

`warn` 覆盖可疑但不致命的情况：提示词有未替换的占位符、模型没按 YAML 格式返回、画像引用了不存在的 msgid（会列出被丢弃的 id）、子任务失败导致报告某段留空、出图失败回退为文字。

出错时一律打全文不截断：没按格式返回时打完整响应，YAML 语法错时打完整 YAML，接口返回空时打完整响应体（含厂商的 error 字段，比如 `insufficient_quota`）。请求超时或中断时先打一行归纳好的原因（`HTTP 429 | UND_ERR_HEADERS_TIMEOUT | ...`）再打原始错误对象，不用自己在层层嵌套的 `cause` 里翻。

`debug` 会额外打印**完整提示词**和生效配置——提示词里含几百条群消息，很吵，按需开启。API Key 在任何级别都不会进日志。

嫌 `info` 里的完整响应太吵，把 `llm/index.ts` 里那两行 `完整响应` / `解析出` 的 `log.info` 改回 `log.debug` 即可。注意 reggol 对**单行**超过 10240 字会截断，YAML 是多行的所以不受影响。

## 目录结构

```
src/
├── index.ts            插件入口：装配各模块
├── types.ts            跨模块共享的领域类型
├── logger.ts           具名 logger，统一日志来源
├── time.ts             时区绑定的时间格式化（纯函数）
├── text.ts             表情、提及等内联标记与占位符（纯函数）
├── transcript.ts       投喂给模型的对话文本排版（纯函数）
├── markdown.ts         QQ markdown 转义与封装（纯函数）
├── config/
│   ├── index.ts        配置接口与 Schema
│   └── prompts.ts      提示词模板默认值
├── database/
│   ├── index.ts        建表
│   └── tables.ts       表名常量与记录类型
├── llm/
│   ├── index.ts        LLMService：OpenAI 兼容调用、并发闸门、重试
│   └── prompt.ts       占位符填充、YAML 提取、错误归类（纯函数）
├── message/
│   ├── recorder.ts     消息监听、过滤与序列化
│   └── retention.ts    过期消息清理
├── analysis/
│   ├── group.ts        群分析与高光对话编排
│   ├── persona.ts      用户画像编排
│   ├── stats.ts        发言统计（纯函数）
│   └── report.ts       markdown 报告渲染（纯函数）
├── render/
│   ├── html.ts         图片版面的 HTML 拼装（纯函数）
│   ├── theme.ts        三份样式表与页面模板，以及占位符填充
│   └── image.ts        puppeteer 截图，失败返回 null 由调用方回退
└── commands/
    ├── analysis.ts     群分析 / 自由问答
    ├── highlights.ts   高光对话
    ├── persona.ts      用户画像
    └── target.ts       解析分析目标与群名

client/                 控制台扩展（版面预览）
├── index.ts            扩展入口：注册 plugin-details 插槽
├── mount.ts            Vue 壳，把 React 根挂进控制台
├── Launcher.tsx        设置页上的入口按钮，管预览窗口的开关与刷新

├── sample.ts           预览用的示例数据
├── env.d.ts            .vue / .css 等模块的类型声明

```

依赖是单向的：`logger`、`types`、`text`、`transcript`、`markdown`、`time` 是叶子，`config`、`database` 只依赖它们（外加 `render/theme` 里的两份模板默认值，与 `config/prompts.ts` 同理，只是常量），`llm` 与 `message` 建立在这之上，`analysis` 与 `render` 再往上，`commands` 位于最外层。统计与两种渲染（markdown / HTML）都被拆成不依赖 `Context` 的纯函数，可以脱离 Koishi 单独测试。
